PROJECT 03

Break/Fix Incident Simulation

A set of realistic, timed incidents that demonstrate methodical troubleshooting, escalation judgment, clean ticket notes, and root-cause analysis.

TroubleshootingIncident responseRCATicket notesRunbooksPlanned — update after completion

Objective

Create a repeatable incident lab using your network and Linux environments. Have a friend—or ChatGPT using only your approved fault list—select a hidden failure. Diagnose it under a time limit, restore service, and document the exact evidence used.

Why this matters

Data center work is operational. Hiring teams want to see that you protect service, follow process, avoid random changes, communicate impact, and verify recovery after a repair.

Lab design

  • A catalog of at least ten faults divided across physical, network, operating-system, service, and storage categories.
  • A severity and escalation rule for each scenario.
  • A ticket template with impact, timeline, observations, actions, results, and handoff fields.
  • A troubleshooting flow that starts with scope and recent changes before making fixes.
  • A root-cause template that separates trigger, root cause, contributing factors, resolution, and prevention.

Build sequence

  1. Create the fault catalog but hide the selected fault during each exercise.
  2. Record the start time, reported symptoms, affected systems, and initial impact statement.
  3. Gather evidence before changing configuration: link state, IP settings, reachability, service status, disk, logs, and recent changes.
  4. Form and test one hypothesis at a time; record rejected hypotheses.
  5. Restore service using the lowest-risk change available.
  6. Run post-recovery validation and monitor for recurrence.
  7. Write a short customer/manager update and a detailed technical handoff.
  8. Complete an RCA for the best three incidents and create one prevention runbook.

Acceptance tests

  • The final ticket clearly shows impact, timestamps, evidence, actions, and validation.
  • Every configuration change has a reason and recorded result.
  • The selected fault is correctly identified without relying on a full rebuild.
  • The service is validated from the user side, not only from the affected device.
  • The RCA identifies a preventive control or monitoring improvement.

Resume bullet — use only after completion

Diagnosed and resolved simulated network, Linux, service, and storage incidents using evidence-driven troubleshooting; produced time-stamped ticket notes, post-recovery validation, root-cause analysis, and preventive runbooks.

Evidence checklist

  • Fault catalog
  • Three completed incident tickets
  • One full root-cause analysis
  • Before/after command output
  • Service validation evidence
  • Escalation and handoff message
  • One preventive runbook
  • Reflection: what you would do faster next time
